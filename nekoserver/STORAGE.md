# Storage and scheduled work

| Content | Working location | Backup policy |
|---|---|---|
| Music audio and downloads | SSD `library/music` and `library/downloads/music` | No automatic file backup, including monthly snapshots |
| Music application settings/accounts/playlists | SSD appdata | Existing application-state backup policy |
| Immich photos/videos | SSD `photos/immich-library` | Weekly add-only originals copy to the HDD and to the USB drive; weekly Immich database dump on the SSD and HDD (newest `photos.database_keep` dumps kept, default 4) |
| Movies/shows and their downloads | HDD library | No media-file backup; application state remains protected |
| Nextcloud files | HDD `cloud/files` | Weekly add-only copy of each user's files to the USB drive, with a list of the files you had at each copy (for "as of" restores, RECOVERY.md) |
| Media app settings and databases (Jellyfin, Navidrome, Sonarr, Radarr, Lidarr, Prowlarr, Seerr, qBittorrent) | SSD appdata | Nightly app-state snapshot and monthly pre-update snapshot, both on the HDD |
| Immich database and settings | SSD appdata | Weekly database dump (see the photos row, also copied to the USB drive) and the monthly pre-update snapshot on the HDD; not in the nightly snapshot |
| Nextcloud database and settings (users, shares, calendars, contacts) | SSD appdata | Weekly database dump on the HDD, also copied to the USB drive (newest 4 in each place), made by the weekly USB backup, so only when the USB backup is set up; and the monthly pre-update snapshot on the HDD. Not in the nightly snapshot. Without a USB backup only the monthly snapshot has it |
| Container images | Docker on the SSD | The images in use at each monthly snapshot, in its `images.tar` on the HDD |
| OS and user settings (Steam, Samba) | OS disk, home | Nightly host-state snapshot on the HDD |

**What goes where.** The USB drive holds the weekly add-only copies of Immich photos/videos and Nextcloud user files, plus the newest 4 weekly Immich database copies, each with a note of the Immich version that made it and its checksum, so it can rebuild Immich on its own (RECOVERY.md, "Rebuild Immich from the USB drive"), and the newest 4 weekly Nextcloud database copies (RECOVERY.md, "Nextcloud's database"). Each weekly copy of the photos and of the Nextcloud files also writes a list of the files you had then (`.neko-inventory/`), so a restore can leave out what you deleted or renamed. The HDD holds the software side (app settings, databases, container images, OS/user settings) and the same add-only Immich photo copy plus the Immich database. "Add-only" means new files are added and nothing on the backup is ever overwritten or deleted: a file that changed (an edited document, an updated photo sidecar) is kept next to the old one as `name.neko-<date>.ext`, and a hidden `.name.ext.neko-latest` note records which copy is current. Since 0.28.7 the folder's hidden `.neko-names.json` also records which file each dated copy belongs to, so a file that only *looks* dated (one you named `report.neko-20261022T120000Z.txt` yourself) is restored as a file of its own, never merged into `report.txt`. A dated copy counts as a version only when the backup recorded it (or its note names it as the current copy); an older version from before that record began comes back as a file of its own too: at worst an extra file, never a lost one. Names may be as long as Linux allows (255 bytes): when a dated name would be longer, its start is kept with a short code (`Long name…~1a2b3c4d.neko-<date>.docx`) and the full name is written down in the folder's hidden `.neko-names.json`, so a restore puts the file back under its own name. **A file that became a folder (or a folder that became a file).** Delete a file `Projects` in Nextcloud and make a folder `Projects` (or the other way round), and the old one on the USB drive would stand in the new one's way. The weekly copy moves the old one, with its dated copies and their checksums, into `neko-replaced/<date>/` beside that user's `files` folder (the same path inside), then copies the new one; nothing is deleted, and the next run is not blocked. Restoring that user's files brings these back too, in a folder called `replaced earlier`. Only NekoServer's own bookkeeping files are left out of a restore (the checksum list, `.neko-names.json`, the `.neko-latest` notes and unfinished `.neko-part` copies); a file of yours that happens to start with `.neko-` is restored like any other. The weekly USB copy needs only the apps you set up: with Nextcloud and no Immich it copies just the Nextcloud files (and with Immich and no Nextcloud, just the photos). The USB drive must be a disk of its own: setup and every weekly run refuse a partition of the system disk, the SSD or the media HDD (when Linux itself is on a Btrfs pool over several disks, each of them counts as the system disk). Damaged copies are handled as described in "How backups are verified" below. Nextcloud previews, trash and caches are not copied; group folders are not covered.

**When the PC starts.** The SSD and HDD are mounted from lines NekoServer adds to `/etc/fstab` (the file of drives Linux mounts at startup; the original is kept once as `/etc/fstab.nekoserver.bak`). Each drive gets up to 90 seconds to appear, enough for a big hard drive or one in a USB case to spin up. If a drive still doesn't appear, the PC starts anyway, but Docker and the apps stay stopped until it is back, so nothing is ever written to the system disk by mistake. Plug the drive in (or check its cable) and restart. A Btrfs drive that was already mounted with a subvolume when you picked it keeps that subvolume (saved as `"subvolume"` under the drive in your settings), so a restart mounts the same tree; every check that the right drive is mounted (setup's, the backups' and Docker's start check) also checks that subvolume. An encrypted (LUKS) drive, or an LVM volume or RAID array on encrypted drives, must be unlocked by Linux at every start: listed in `/etc/crypttab` without the `noauto` option. Setup says which one is not, also for a drive already in your settings (settings reused after reinstalling Linux, with the drive opened by hand). **A Btrfs pool over several drives** is recognised by its UUID, whichever of its drives Linux names as mounted. When the pool holds Linux itself, every drive of it counts as the system disk. Setup tells the drives of a pool from copies of one drive by each drive's own Btrfs device ID; it can read that ID only with `sudo`, and says so instead of calling the drives copies. **A copy of the SSD or HDD left connected** (made with `dd` or Clonezilla) carries the same UUID, and Linux mounts the drives by UUID, so it could mount the copy instead. Docker's start check and setup's drive check refuse then: "Two drives look the same (one is probably a copy); unplug the copy". The drives of one Btrfs pool are not copies. If the check can't be made (lsblk or blkid can't say), the drive is used as before. Only a whole drive (or, on Btrfs, a subvolume) can be the SSD or HDD: when just a folder of an ext4 or XFS drive is mounted at the drive's folder, setup stops and says to unmount it. The disk Linux runs from is never offered as the SSD, HDD or USB drive: any disk with a partition mounted at `/`, `/boot`, `/efi` or `/boot/efi` (all the places a Btrfs system partition is mounted are looked at, not only the first).

Navidrome, Lidarr and the qBittorrent music category use the SSD. Local imports route music to SSD and videos to HDD. Incomplete downloads may use the configured shared temporary folder. No watched-video migration between SSD/HDD is performed.

## How backups are verified

Every backup tree (the photo archive on the HDD, its copy on the USB drive, and the Nextcloud copy on the USB drive) has a **checksum ledger**, `.neko-ledger.json`, at its root.

- **Recorded once, never replaced.** Every checksum is SHA-256. A file's checksum is recorded the moment a copy of it is first verified. It is never updated afterwards, even when the file on a drive changes, so damage can never become the "expected" content.
- **Unverified until confirmed.** Files backed up before the ledger existed have no checksum. They stay *unverified* (the dashboard log says how many) until two independent copies agree: the archive file and the Immich original, or the HDD and USB copies. Then the agreed checksum is recorded.
- **Every copy is checked three ways.** The data is hashed while it streams into a temporary file, the file is fsync'd and read back from disk, and the source is hashed again. The file is published (never over an existing one, then the folder is fsync'd) only when all three match and the source did not change during the copy (same size, modification and status-change times).
- **The ledger is written last.** It is written to `.neko-ledger.json.<uuid>.tmp`, fsync'd, renamed and the folder fsync'd, always after the files it lists. Only one job writes it at a time.
- **Two ledgers back each other up.** The USB copy of the photo archive has its own copy of the ledger. A record either one has is kept in both: if the HDD's ledger is lost or incomplete, the USB's records still say which copy is good (and the HDD's ledger takes them back), and a run that fails part way leaves the USB's ledger as it was. If the two ever record different checksums for a file, neither decides: both copies are kept and reported. **Repair damaged backup copies** then shows each copy with the list it matches and asks which one is right (or keeps both as they are); only the copy you choose is recorded in both lists afterwards. A USB ledger that can't be read is kept aside as `.neko-ledger.json.unreadable-<time>`, never written over.

When copies disagree, the ledger decides:

| HDD archive | USB copy | What happens |
|---|---|---|
| matches | matches | Nothing to do |
| matches | damaged | The USB copy is moved to `neko-damaged/<time>/` on the USB drive and copied again from the HDD |
| damaged | matches | The USB copy is kept; the HDD file is reported as damaged and never copied onto the USB drive |
| damaged | damaged | Both are kept untouched and the job fails with a CRITICAL message |
| no checksum, copies equal | | The checksum is recorded |
| no checksum, copies differ | | Both are kept untouched and reported |

A damaged archive file whose Immich original still matches the ledger is replaced from the original (the damaged one is kept in `neko-damaged/` on the HDD). Damage fails the job with the file names after the rest of the copy has finished. A damaged first copy never stops the file's later versions from being saved: when the original was edited since, the new content is still saved as a dated version (`name.neko-<date>.ext`), and the damage is still reported.

**Seeing and fixing problems.** The dashboard's Backups page shows the result of each tree's last check: intact, how many files are not verified yet, and any damaged or mismatched files. An alert is raised when anything is damaged. To fix them, run `sudo bash install.sh --recover` and choose **Repair damaged backup copies**:
- A file with a recorded checksum is fixed from whichever copy still matches it: the HDD, the USB drive or the Immich original (Nextcloud: the live Nextcloud file).
- If none matches (or the saved copy is gone), it can't be repaired. This is common for Nextcloud files, whose only backup is the USB drive: the file was edited or deleted since, or the damaged copy is an older dated version. You choose: **Keep it as it is for now**, or **Accept that this saved copy is lost**. Accepting moves the copy to `neko-damaged/<time>/` (kept, never deleted) and takes it off the checksum list, with a record of when and why (`"retired"` in the list). The checks then pass again, and the next weekly copy saves the file's current content anew. Until you decide, the monthly check finds the same damage every month and stops the monthly snapshot and updates; its message says to use this option. A photo copy is offered as lost only with the USB drive plugged in, so its second copy is looked at first.
- A file with no recorded checksum whose copies differ is settled by the Immich original when it matches one of them; otherwise you choose the right copy. Its checksum is then recorded.
- Damaged copies are moved to `neko-damaged/<time>/`, never deleted.

**Missing files.** Every run also compares the ledger's list with the files actually there. A backed-up file missing from the HDD archive whose USB copy still matches is reported as missing (repairable from the USB drive); a file gone or damaged everywhere is critical. A restore stops before copying anything if a file the ledger lists for that folder is missing.

**Fast checks and deep audits.** Path, size, modification time and status-change time are used only to skip files that have not changed since they were last copied. They never prove that a file is intact. Files named by a current-version note are read every week. Once a month, as the very first step of the monthly run, every copy on the HDD and (when it is plugged in) the USB drive is read in full and compared with its recorded checksum, which finds silent bit rot that leaves size and dates unchanged. Only then does the monthly run take its backup and install updates; damage found stops it before either, and the dashboard says which files. The hourly and weekly copies never do this full read, so they stay quick.

**Restores.** The recovery wizard checks every file it restores against the ledger of the backup it reads from. A damaged file, an unreadable file or folder, or a symlink in the backup stops the restore with the file named; nothing is restored from a partial list. Files without a recorded checksum are restored and counted as unverified. Paths in a ledger must be plain relative paths (no `/` at the start, no `..`), or the whole ledger is refused.

## Weekly photo protection

The combined originals/database worker runs **Sunday at 02:15** in your configured `timezone`. It copies mature originals additively from SSD to HDD, verifies bytes, creates the logical database dump, and verifies database copies on SSD/HDD. Both operations use one worker and recovery lock.

**Immich is paused for a moment each week.** So the photo copy and the database copy are of one point in time, the weekly run works in two passes. First, with Immich running, it copies the new photos and videos (files changed in the last 10 minutes wait: they may still be being uploaded). Then it notes what runs (`/etc/nekoserver-backups/immich-resume.json`), stops Immich's server and machine-learning containers gracefully (the database keeps running), checks with Docker that none of them still runs (otherwise nothing more is copied and Immich is started again), copies what came in meanwhile (now every file, also the newest ones: nothing can be half-written while Immich is stopped), makes the database copy and starts Immich again. The week's backup counts as done only when both the photo copy and the database copy were verified. A photo upload cut off by the pause may leave a partial file that is copied too; Immich doesn't list it, and the phone sends it again. The pause is usually a minute or two; the log says how long it was. Uploads from the phone app wait and continue by themselves. Immich is started again whatever happens: also when the copy or the database copy fails, the job is stopped, or the power goes (a note in `/etc/nekoserver-backups/immich-resume.json` says what to start; the job's own stop step and `nekoserver-immich-resume.service` at the next start use it). If Immich was not running when the job started, it is left stopped. Why this order: a restore from the USB drive alone uses the newest database copy and the photo copy beside it, so no photo the database names may be missing from the copy. Damage found in the photo copy is reported, but never keeps the database copy from being made. A file that became a folder (or a folder that became a file) in Immich's library is moved aside into `neko-replaced/<date>/` at the archive's top, as for Nextcloud files, and the USB copy follows; restoring photos brings these back too, in `replaced earlier`. A partial copy left by a run that was cut off (`.neko-<code>.neko-part`) is removed by the next run, also when its file was deleted meanwhile. A database copy that was cut off (a power cut) leaves an `immich-<date>.sql.part` file; the next run removes it once it is over an hour old. The database copy also has its own 30-minute limit inside the database container, so a copy that hangs is really stopped there. The dashboard's archive/database cards use this combined result and weekly overdue thresholds.

The USB copy runs **Sunday at 03:00**. When the photo job is still running then (a first big archive, say), it waits for it to finish (up to six hours) and then copies everything, instead of failing; a restore from the USB drive in the recovery menu is waited for the same way. The correct external disk must be connected; otherwise the run fails visibly without writing to the OS disk. All managed photo timers are weekly, with daytime catch-up disabled. A missed scheduled week waits for the next scheduled run unless started manually. Files modified in the last ten minutes are deferred for stability (the job log counts them). A photo dated in the future (a camera or phone with a wrong clock) is copied at once, not deferred until that date comes; every copy is checked byte for byte anyway. A photo or folder deleted, renamed or changed while it is being copied is left for the next run (the job log counts these) instead of failing the whole run. New uploads can therefore wait roughly a week for an independent server copy.

The weekly USB copy no longer holds the shared lock for the whole copy (a first or big copy can take hours, and the nightly backups and setup had to wait that long and then failed): it waits for the lock only to check that no monthly update is under way, then lets it go. If it cannot start because of that (or the wait runs out), the dashboard shows the reason like any other failed run. Nextcloud files whose names are not valid text (UTF-8, usually from an old system with another character set) are left out and named in the report as "names not supported" instead of stopping the whole Nextcloud copy; rename them. When a copy on the backup is dated after the current time (written while the clock was ahead), the quick weekly check compares it by content instead of trusting its date. Monthly cold full-state snapshots and isolated recovery tests remain enabled.

The previous frequent photo archival timer is disabled/stopped on apply. The formerly daily database timer is rewritten as weekly. Immich's own internal SSD-local database backup feature is separate from these managed server-to-HDD/external copies.

## Removed recurring work

`monitoring.enabled: false` disables and stops the old NekoServer media-health timer/worker. There is no replacement every-six-hours media audit. Monthly pre/post-update connection checks and ad hoc diagnostics remain available. The dashboard continues lightweight host/container-status collection and reports routine media checks as disabled; it does not show stale old API audit failures.

When the opt-in music backup runs, music files changed in the last ten minutes (an album still being added) wait for the next run and are listed in the job log; the rest is backed up, instead of the whole run failing. A file dated far in the future (a wrong clock) is backed up at once. Only the waiting files are left out of that run's catalogue; anything changed while it copies still fails the run, as before. `music.backup_enabled: false` disables/stops the music backup timer/worker. Monthly recovery excludes raw music and music downloads too. Application accounts/playlists/settings still receive the existing state backups. Previous backup files are preserved; no user data is deleted. The opt-in backup CLI/restore reader remain available for explicit manual use/old inventories.

The cleanup modules remain in dependency plans so applying the current full/media/music installer can retire old timers. Managed unit files are recognized before service changes; custom administrator files are preserved and reported for review. A disabled timer is checked as absent/inactive during acceptance, rather than required to be active.

## HDD and unchanged jobs

The guarded native SATA standby timer remains **60 minutes** (`hdparm -S 242`), with no PC sleep. SMART queries avoid waking a standby disk. Playing HDD videos, Nextcloud activity, torrent seeding, app-owned scans, nightly application/host-state backups, weekly photo copies and monthly maintenance can still wake it. Removing NekoServer's periodic media audit cannot prevent ordinary application activity. Native power behaviour and wake latency need testing on the target PC. Every drive of a Btrfs HDD pool gets the timer, not only the one Linux names as mounted. An encrypted (LUKS), LVM or RAID HDD keeps its own power settings ("left to the drive itself"), and the power service no longer fails for it.

Nightly app-state/host-state backups and monthly overnight recovery/update work are unchanged. Scheduled orchestration remains Rust; Python handles installation and ad hoc recovery. No OS upgrades or automatic formatting are added. Snapshot retention is described in MONTHLY-MAINTENANCE.md, APP-BACKUPS.md and HOST-BACKUPS.md; add-only photo and Nextcloud copies are never pruned.

## If a drive disappears

When the SSD or HDD disappears while the server runs (unplugged, a loose cable, a USB case that reset), Docker stops and every app with it: nothing may be written in the drive's place on the system disk. The backups refuse to run, and the dashboard shows the drive as unavailable. A drive (the SSD, the HDD or the USB backup drive) that drops out while a backup is already copying stops that backup with a message naming the drive: every folder and file it makes is first checked to still be on the drive the run started with, so it never carries on writing into the empty folder left on the system disk. A drive that hangs instead of going away shows as unavailable on the dashboard after a few seconds, and the rest of the dashboard keeps updating.

Reconnect the drive. The *nekoserver-drive-return* service runs as soon as the drive appears: it releases the mount the drive left behind, mounts it again, checks that both drives are the ones chosen at setup, and starts Docker, the shared folders and the home gateway again. If the drive went while a backup or the monthly update had the apps stopped, it then finishes that job the way a restart would (the monthly update first, which may roll its update back, then the nightly snapshots), so the apps it stopped start again. The apps are back within a minute or two (longer when a monthly update has to roll back). If they are not, restart the PC; to see what it did:

```bash
sudo journalctl -u nekoserver-drive-return.service
```

## Existing installations and recovery

Applying this release updates schedules and retires the recognized old timers. Existing old HDD music/Immich working layouts still require the verified, stopped-writer migration described in the prior release; different manifests or environment paths are preserved/refused. Do not switch a mount to an empty SSD folder and assume files moved.

Monthly recovery covers selected app state and databases (including Immich's and Nextcloud's) and exact old images. Since v0.21.1 it no longer contains the Immich photo library or Nextcloud files; those are restored from the weekly add-only copies. Raw audio/movie/show files are outside rollback coverage. Restored test stacks use isolated empty read-only substitutes for excluded media folders. Old-version durable recovery journals must be handled by their matching release; a changed version refuses them without replacing live state.

## If Docker is already used on this PC

NekoServer runs Docker from the SSD. When Docker was already set up on this PC before (its data in `/var/lib/docker`, or in another folder named as `"data-root"` in `/etc/docker/daemon.json`), setup stops at the Docker step and says so: it never moves or deletes existing Docker data by itself.

A Docker with nothing in it (no container, image or volume: the package just installed, or NekoServer uninstalled) is not "already used": setup stops it and runs it from the SSD from then on. The message above comes only when something is in it.

If nothing in that Docker needs keeping (you only tried it out, say), put its data aside and run setup again:

```bash
sudo systemctl stop docker.service docker.socket
sudo mv /var/lib/docker /var/lib/docker.before-nekoserver
sudo bash install.sh
```

Use the folder the message names if it isn't `/var/lib/docker`, and remove the `"data-root"` line from `/etc/docker/daemon.json` if it has one. Nothing is deleted: the old folder stays where you moved it until you remove it yourself.

If you run containers there that you want to keep, note what they are (`docker ps -a`) and where they keep their files first. After NekoServer's setup they run from the SSD: create them again there, pointing at the same files.

## Private account inventory

The secrets/accounts directory is included in monthly snapshots on the HDD, encrypted, and opens with the backup password chosen during setup (see MONTHLY-MAINTENANCE.md, also for what happens without one). It is never written to the USB drive. See ACCOUNT-SETUP.md.
